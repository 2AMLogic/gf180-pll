- **Methodology / criteria / limitations**:
  - **Mechanism added, and why it is additive, not a deck change (#168's
    third acceptance criterion)**: `sim/lib/simenv.sh`'s `simenv_run_deck`
    gained an optional `SIMENV_RUN_TIMEOUT_S` env var (unset by default, so
    every other caller -- every other row of every closed-loop campaign --
    is byte-for-byte unchanged) that wraps the `ngspice` invocation in GNU
    `timeout --signal=TERM --kill-after=10 <N>`; `ngspice` is `timeout`'s
    DIRECT child in that subshell (no intervening bash layer to swallow the
    signal), so the cap terminates the simulator itself rather than
    orphaning it. `sim/output-range/testbench/run.sh` exposes this as
    `SIM_TIMEOUT` (seconds), following `SIM_WINCAP`'s exact precedent: it is
    appended to the work-directory tag (`_cap<N>s`) whenever set, so a
    capped log can never be silently read as a simulator-reached verdict,
    and it is absent from the tag (default tags unchanged) whenever unset.
    Verified this session that an ordinary row (`ff`/27 C/2.97 V `hi`, run
    fresh under ngspice-46) reproduces its committed grid-record row
    exactly (`vctrl_final=1.21219 V`, `FAIL`/`PASS` DN guard, ~237 CPU-s)
    with `SIM_TIMEOUT` unset, and that a deliberately tiny cap
    (`SIM_TIMEOUT=5`) on that SAME row now classifies as a capped `ERROR`
    within seconds instead of blocking -- the mechanism only fires when
    asked to.
  - **Characterising the stall (#168's first acceptance criterion)**: the
    point's own `ngspice.log` is uninformative about *how far* a killed
    attempt got -- this deck's `.control` block issues one `tran` command
    and `wrdata`s the waveform only at the very end (see
    `tb_output_range.sp`'s header), so a completed run's log and an
    incomplete run's log both consist of the printed t=0 "Initial Transient
    Solution" node table (identical, 441 lines, no anomalous or NaN entries
    -- the DC operating point itself is NOT the problem) followed by
    whatever the run reached before it stopped; there is no per-timestep
    progress line either way. The stall time was instead bracketed by
    running the SAME point at a deliberately shortened transient window
    (`SIM_WINCAP`, already documented in `run.sh` as a diagnostic-only knob,
    unmodified by this record) under a wall-clock bound, off the same
    committed deck:

    | `SIM_WINCAP` (simulated window) | wall-clock bound | outcome |
    |---|---|---|
    | 10 ns (0.5% of the full 2 us window) | 90 s | did not complete |
    | 50 ns | 90 s | did not complete |
    | 100 ns | 90 s | did not complete |
    | 200 ns | 200 s | did not complete |
    | 500 ns | 200 s | did not complete |
    | 800 ns | 200 s | did not complete |
    | 2000 ns (full window, this record's official row) | 1800 s | did not complete |

    For comparison, the SAME corner/edge's supply neighbour
    (`ff`/27 C/2.97 V `hi`) completes its FULL 2000 ns window in ~237 CPU-s
    (~253 s wall, measured fresh this session under ngspice-46 -- consistent
    with `20260819-160843-4e32f91.md`'s cited 220.6 CPU-s). **A window
    0.5% the size of the full transient already exceeds that entire
    healthy-corner budget without completing.** The honest conclusion is
    narrower than "stalls at simulated time T": the collapse is present
    from very early in the transient (within the first tens of nanoseconds,
    likely well under 10 ns), not a late-stage phenomenon that only appears
    once the loop has run for a while -- contrary to the loose "gets past
    the DC operating point and then grinds" framing in #168's own Problem
    section, which this record's bisection does not bear out; the correct
    statement is "gets past the DC operating point and grinds almost
    immediately."
  - **What drives the internal timestep down (#168's first acceptance
    criterion, second half) -- partially answered, honestly**: the two
    existing `ERROR` rows in `20260819-160843-4e32f91.md` (`sf`/27 C/2.97 V
    and `sf`/27 C/3.30 V, `lo`) are ngspice's OWN verdict -- both abort
    after ~8 CPU-s with an explicit `Timestep too small; time = ...:
    trouble with node "vs4#branch"` message. This point never reaches that
    self-diagnosing failure state in any tested bound: it just keeps
    running. To test whether the mechanism is the same family (repeated
    Newton-iteration non-convergence forcing step-halving until ngspice
    gives up), a SCRATCH copy of `tb_output_range.sp` (never committed, not
    part of this record's deck) with `itl4` lowered from the committed
    200 to 8 was run at `SIM_WINCAP=50e-9`: if per-step Newton
    non-convergence were the driver, cutting the allowed iterations 25x
    should make ngspice give up and report the trouble node much sooner.
    It did not -- no error, no completion, in 280 CPU-s for a window that
    should cost a healthy corner a small fraction of a second. This rules
    out per-step Newton-iteration exhaustion as the (sole) mechanism and
    points instead at the LOCAL TRUNCATION ERROR (LTE) step-size
    controller choosing an extremely fine step for a sustained span of
    simulated time even though each individual step converges --
    qualitatively different from the `sf`/`lo` rows' fast, self-diagnosing
    convergence aborts. **This record does not isolate the specific
    node/branch driving that LTE collapse** -- doing so would need
    instrumented/debug-build ngspice internals, out of scope for a bounded
    diagnostic investigation. The most plausible candidate, offered as a
    hypothesis and NOT confirmed, is the loop filter's nonlinear MOS-cap
    varactors (`cap_nmos_03v3_b`, instances `XCF1`-`XCF4` in
    `design/netlist/pll_top.spice`'s `loop_filter` subcircuit): this is the
    SAME element `tb_output_range.sp`'s own `.options` comment already
    names as this DUT's historically fragile numerical branch (without
    `rshunt=1e12` the migrated deck aborts inside the SWFORCE release ramp
    "on the loop filter's nonlinear moscap branch"). Against this
    hypothesis: `sim/vco-tuning-range`'s own open-loop Kvco table for this
    corner (`ff`/27 C/3.30 V, band 7) shows no sharp discontinuity near this
    row's 1.454 V seed (Kvco varies smoothly from 1.15e8 to 1.24e8 Hz/V
    across the 1.2-1.5 V bracket) -- though that measures the VCO's
    frequency sensitivity, not the loop filter node's own local C-V
    curvature, so it does not rule the hypothesis out either. Left as
    honestly unresolved rather than asserted.
  - **Why a fix was not pursued**: isolating and correcting an LTE-driven,
    non-self-diagnosing convergence collapse (as opposed to a Newton
    non-convergence ngspice reports on its own) would require either
    instrumented ngspice internals or a materially different solver
    configuration bisected specifically for this one point -- exactly the
    kind of per-point tuning `tb_output_range.sp`'s own `.options` comment
    and #159's bisection explicitly reject ("every convergence TOLERANCE is
    this campaign's own... bisected for the campaign as a whole, not per
    point"). #168's own acceptance criteria accept a reproducible bounded
    outcome as an alternative to a fix; that is what this record delivers.
  - **The official evidence row**: `SIM_TIMEOUT=1800` (30 minutes) against
    the unmodified committed deck. The process accumulated at least
    1725 CPU-s (28 m 45 s, ~96% single-core utilisation) before the cap
    terminated it at 29 m 52 s wall -- comparable in both CPU-s and
    CPU/wall ratio to the original uninterrupted attempt's 151 CPU-min /
    3 h 00 m wall (~84% utilisation), and its `ngspice.log` is, again, just
    the 441-line t=0 operating-point dump with no completion banner. This
    is a **deterministic, reproducible** outcome: re-running the exact
    command below reproduces the same cap-triggered `ERROR` without any
    manual intervention, unlike the predecessor record's manually-killed
    row.
