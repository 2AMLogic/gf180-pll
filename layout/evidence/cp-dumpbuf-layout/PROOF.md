# `cp_dumpbuf` block layout — DRC run (issue #302)

Part 4 of #294 (itself one of #292's five block sub-issues): a real,
transistor-level layout for `design/cp_dumpbuf.sch` — the charge pump's
dump-node tracking buffer (DR-005's fix for the charge pump's dominant
systematic error, see that schematic's own text annotation for the full
circuit rationale). Generated by
`layout/pll_top/pfd_cp/cp_dumpbuf.py` and checked with

```
python3 layout/run_pv.py drc <gds> --top cp_dumpbuf --run-dir <dir>
```

against the gf180mcu PDK's own foundry DRC deck (not `klt drc`'s curated
subset — see `layout/README.md`'s "Why this isn't `klt drc`" section).

## What this is, and is not

Every device is transcribed directly from `design/cp_dumpbuf.sch`: two
complementary 5-transistor OTAs in unity-gain feedback on the shared
`VDUMP` node — `MTN`/`MN1`/`MN2`/`MN3`/`MN4` (NMOS-input pair, PMOS mirror
load) and `MTP`/`MP1`/`MP2`/`MP3`/`MP4` (PMOS-input pair, NMOS mirror
load). All ten transistors are `nfet_03v3`/`pfet_03v3`. This is a
**DRC-clean geometry claim only** — LVS (netlist-match against
`design/cp_dumpbuf.sch`) is not run here and is not claimed; it was not
part of this issue's acceptance criteria (unlike #299's proof cell, which
required both). `layout/pll_top/pfd_cp/cp_dumpbuf.py`'s own module
docstring records the layout-vs-schematic difference LVS would need to
reconcile: `MTP` (schematic `W=48u`) and each of `MP1`/`MP2` (schematic
`W=48u`) are drawn as two 24 um-wide parallel fingers rather than one
`nf=1` instance — total `W` and device count are preserved (electrically
identical to two `nf=2`-folded devices), the same recorded difference
`layout/pll_top/vco/mirror.py`'s own "Cascade B" note documents for its own
folded leg.

**`klt gen`/`klt gen-compose` vs. direct `klayout.db`, per this issue's own
"document the choice either way" note.** Issue #299's own `devgen.py`
(Part 1, merged via PR #312) already tried and rejected the `klt gen
mos_array` → `klt gen-compose` round trip for this device family — see that
module's own docstring for the full six-rule-family DRC-deck gap and the
generic tool-gap issue it filed (2AMLogic/klayout-tools#1575). This issue's
own body named `klt gen diff_pair`/`well_island` as candidates for the
common-centroid pair and the isolated well specifically; both were
considered against `devgen.py`'s already-proven direct-`klayout.db` leaf
cells (`MP1`/`MP2` still need `devgen.mosfet()`'s own DRC-clean device
geometry underneath either path) and the isolated-well requirement itself
(a caller-supplied separation constraint against other wells) is exactly
`well_island`'s own stated purpose — but composing `well_island`'s
guard-ring-based island with `devgen.py`'s already-DRC-clean device stack,
for a >2-terminal-net, two-row netlist `devgen.build_stack_cell()` itself
cannot resolve (see `cp_dumpbuf.py`'s own module docstring, "WHY THIS ISN'T
A `build_stack_cell()` CALL"), was not attempted: this issue's own
Dependencies section already established that `devgen.py`'s own
`mosfet()`/`Canvas`/`Device` primitives are Parts 2-4's shared,
already-DRC-proven foundation, so this module draws the isolated well
directly against the same primitives (its own margin, docstring-cited
against `NW.2b`) rather than mixing two different generator families in one
cell. If a real capability gap surfaces in a future increment that composes
`klt gen`'s isolated-well output with hand-drawn devices, it will be filed
generically per the friction protocol at that point — none was reproduced
by this issue's own work.

**Isolated-well separation.** Per DR-005 (cited in `PLL-FLOORPLAN.md` §4):
`MP1`/`MP2`'s bulk is tied to their common source `PSRC`, not `VDD`, so
they are drawn in their own isolated n-well, common-centroid (`MP1a
MP2a MP2b MP1b`), checked disjoint from every *other* n-well this cell
itself draws (`MTPa`/`MTPb`'s and `MN3`/`MN4`'s own `VDD`-tied wells) by
at least `DIFFERENT_POTENTIAL_WELL_MIN_UM` = 1.4 um — gf180mcuD's own
`NW.2b` different-potential n-well spacing rule, the same number
2AMLogic/klayout-tools's `well_island` generator uses as its own
`separation_um` default (see `cp_dumpbuf.py`'s own citation). Part 3
(#301, the CP output-stage arrays) has not landed as of this build, so its
wells cannot be checked against real coordinates yet — `check_well_separation()`
is the general-purpose function that check will use once Part 3's geometry
exists; `layout/tests/test_cp_dumpbuf_layout.py` exercises it today against
a synthetic stand-in well box in the interim, per this issue's own
Dependencies note.
