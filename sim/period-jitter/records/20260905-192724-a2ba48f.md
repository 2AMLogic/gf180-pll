  - WHY A TRANSIENT AND NOT loop-dynamics' SMALL-SIGNAL ANALYSIS. The ripple is a nonlinear, periodic-steady-state effect (once-per-reference-cycle charge-pump event), exactly as sim/reference-spur's own methodology states; sim/loop-dynamics' linearized AC sweep cannot produce it and says so in its own Limitations field.
  - STEADY STATE, NOT LOCK TIME. The control node is released at `vstart` -- sim/reference-spur's own committed per-corner lock-point estimate -- for the same reason sim/reference-spur uses it: this campaign measures a STEADY-STATE property (the locked period sequence), not acquisition time (sim/lock-time, #12, owns that claim), and starting near the lock point reaches steady state for the least simulated time. The residual settling drift this leaves is not assumed away -- `ferr` is measured over a 1 us baseline (`ta`/`tb`) immediately before the measurement window and is reported as a lock-quality gate, exactly as sim/pll-top-smoke's and sim/reference-spur's lock criteria are.
  - MEASUREMENT CRITERION: the reported RMS/pp period jitter and TIE come from every rising mid-supply crossing of `v(clk)` in the measurement window (`wa` to `wb`, 300 output cycles = 2.0 us at 150 MHz), linearly interpolated between the two straddling ngspice timepoints (sim/vco-tuning-range's `_numeric.py:crossings`, the same primitive sim/vco-tuning-range's jitter extraction and sim/reference-spur's TIE cross-check both use). Period jitter is the RMS/pp deviation of the per-cycle period sequence from its own mean; TIE is the RMS/pp deviation of the crossing times from their own least-squares line (removes any residual settling drift from being counted as jitter, the same reason sim/reference-spur's TIE path de-trends by a fit rather than a nominal period). `sim/tests/test_period_jitter_derive.py` replays a synthetic waveform of known jitter through this exact reduction path, off any simulator, before this record's own number is trusted.

DR-002 Decision 5 (spec/decision-records/DR-002-draft-spec-scope-ratification.md) ratifies (status: proposed) a VCO-dominated transient-noise testbench plus a jitter-transfer argument through the closed loop as the intended method for the random component, and explicitly rejects an ngspice AC `.noise` analysis as unsupported for a free-running oscillator's phase noise on this flow. Before writing this deck, `.option TRANNOISE=1` was tried on ngspice-46 (this repo's pinned build) against a trivial R-driven-by-a-DC-source circuit: the resulting transient carried NO noise -- a bit-for-bit flat waveform across the whole run -- so this pinned build does not inject automatic device noise into a `.tran` analysis (or the syntax this build recognizes for it is not `.option TRANNOISE=1`; either way, nothing in this repo's flow demonstrates it working). ngspice DOES support an explicit `trnoise()` PWL source function (confirmed working, injecting a synthesized white/1-f voltage waveform) -- but turning that into a credible DEVICE-noise-EQUIVALENT number requires first calibrating the injected amplitude against a validated noise-PSD measurement of the VCO's dominant noise contributors (thermal + flicker in the current-starved ring's bias and switching devices), which is real, separately-scoped methodology development this record does not attempt. Per sim/README.md's own worked example for this exact scenario ('A recorded methodology gap instead of a number (#13)'), this record states the gap here rather than publishing an uncalibrated, not-credible random-jitter figure.
