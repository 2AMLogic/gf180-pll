  - DUT: design/netlist/vco.spice's `vco` subcircuit (constant-gm bias generator, 3-bit band-select mirror chain, 5-stage current-starved ring, 3-stage tapered output buffer, on-chip decoupling) -- the same block sim/vco-tuning-range characterizes, composed ahead of the fragment via this manifest's `dut` key. This is the entire load; no resistive load, no wire parasitic, and critically no divider-input capacitance (see Limitations).
  - OPERATING POINTS -- `sweeps.edge` has two points, `lo` (band code 0, Vctrl = 0.9 V) and `hi` (band code 7, Vctrl = 2.7 V): the same two fixed extremes of the ratified 0.9-2.7 V control window at the two extreme band codes that sim/vco-tuning-range's own tb_vco_tuning.sp already reports output swing at (its sw1hi/sw1lo/sw7hi/sw7lo measures). These are not the ratified 10/200 MHz output-band edges (that per-corner target-frequency interpolation is sim/output-range's job, closed-loop); they are the ring's own edge-rate extremes -- slowest starved edges at band0's Vctrl floor, fastest at band7's Vctrl ceiling -- which is what a duty-cycle or edge-rate claim is actually about. spec/pll.md's own design basis for the duty target states the expected binding condition is 'the bottom of the band, where the starved ring's internal edges are slowest': `lo` IS that condition; `hi` is the opposite extreme, included so the record brackets both ends rather than reporting only the expected worst case.
  - MEASUREMENT DEFINITIONS -- and a real pitfall this manifest works around. `t_r1`/`t_r2` are the first and second rising half-supply crossings of v(clk) after `tsettle` (`when ... rise=1/2`), so `tperiod = t_r2-t_r1` is unambiguous by construction (rise=2 always follows rise=1 in time). Duty cycle is NOT similarly safe as a `trig ... rise=1 targ ... fall=1` pulse-width measurement: ngspice's trig/targ clauses each search independently from their own `td`, with NO guarantee that `targ`'s crossing occurs after `trig`'s (confirmed empirically while developing this manifest -- an early `hi`-point draft measured `thigh` = -1.33 ns, i.e. the `fall=1` crossing landed 1.33 ns BEFORE the `rise=1` crossing, both legally after the same `td`). So `t_f1`/`t_f2` (first/second falling crossings after `tsettle`) are measured the same unambiguous way as `t_r1`/`t_r2`, and `derive.py`'s `derive_point()` picks whichever of `t_f1`/`t_f2` actually falls inside the `[t_r1, t_r2]` window before computing `thigh = t_f-t_r1` and `duty_pct = 100*thigh/tperiod` -- correct regardless of which the deck's own signal history means the DUT happens to expose first. `voh`/`vol` are the max/min of v(clk) over the settled measurement window -- the loaded rail-to-rail swing. `trise`/`tfall` are 10-90 % transition times of the loaded v(clk) edge and do NOT need the same fix: both thresholds of a `trise` measurement share the same `rise=1` slope direction on what is necessarily the same first rising edge after `tsettle` (10 % is crossed before 90 % on any monotonic edge), so trig/targ's independence is harmless there. `trise`/`tfall` are the drive-strength proxy: a stronger driver produces a faster edge into a fixed load capacitance, the same proxy sim/devchar-delay's fan-out-1 chain (fo1_trise/fo1_tfall) uses for the same reason. `fosc = 1/tperiod` is reported as an integrity check (the corner grid must actually move it) rather than as this record's own claim -- sim/vco-tuning-range owns the frequency claim.
  - TRANSIENT SIZING -- the same shape sim/vco-tuning-range's tb_vco_tuning.sp uses (settle for several periods, stop several periods later, cap the internal step at a fraction of a period so crossings interpolate to well under 1 % of a period), but with the SLOW and FAST frequency estimates kept deliberately separate rather than one f_est doing both jobs: `tsettle`/`ktstop` are sized off a floor estimate BELOW every MOS-bundle corner sim/vco-tuning-range's own measured f(Vctrl) table (record 20260804-162735-72883fb) reports at this (band, Vctrl) point, so even the slowest real corner completes several whole periods inside the stored window; `ktmax` is sized off a ceiling estimate ABOVE every corner at 80 internal steps/cycle, so even the fastest real corner keeps that resolution (sizing it off the floor estimate instead would under-resolve the fastest corner's edges by the same factor the two estimates differ by). `lo` measured 3.54-5.23 MHz: tsettle/tstop from a 3.0 MHz floor, tmax from a 6.0 MHz ceiling. `hi` measured 285-473 MHz: tsettle/tstop from a 250 MHz floor, tmax from a 550 MHz ceiling. The 50 fF CLK load does not move either estimate -- it loads the buffer's output stage only, downstream of the ring, so it cannot feed back into the ring's own oscillation frequency; both margins are headroom against the vco-tuning-range estimate itself, not against the load.
  - Statistical switches: sw_stat_global = sw_stat_mismatch = 0 (nominal per-corner device skew, no Monte Carlo mismatch) -- consistent with sim/vco-tuning-range's own convention for this DUT.
  - LIMITATIONS. (1) The 50 fF load is external only: the on-die divider's own input capacitance (sim/divider-ratio-cell's DUT) is NOT additionally modelled, so every number here is mildly optimistic (faster edges, marginally different duty) relative to the assembled chip -- spec/pll.md's target explicitly budgets for both together and this record measures only the first. (2) MOS-only corner sweep (5 bundles: typical/ff/ss/fs/sf); the two composite all-slow/all-fast bundles sim/vco-tuning-range adds specifically because this DUT's frequency depends on a poly resistor are NOT swept here, so the passive (res_*/moscap_*) axes are left at typical -- a documented, allowed choice per sim/README.md's 'Default corner matrix' hazard note, made here because the claim under test (duty/levels/edge-rate at a fixed load) is a MOS-switching-speed question first; the resistor's effect on Kvco is already sim/vco-tuning-range's own characterization. (3) Only the two Vctrl/band extremes are swept, not the full 8-band x 7-Vctrl grid vco-tuning-range covers for frequency -- a deliberate scope cut to keep this record's point count tractable while still bracketing the expected worst case. (4) Schematic-level: no layout parasitics. (5) Clean supply: DC only, no supply noise or ripple on VDD_VCO. (6) Open-loop: Vctrl is a fixed DC source, not the closed loop's own control node -- this isolates the buffer/load question from loop dynamics, which sim/lock-time and sim/output-range already own.
