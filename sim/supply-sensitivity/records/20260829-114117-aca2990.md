# Record 20260829-114117-aca2990

- **Record ID**: 20260829-114117-aca2990
- **Claim**: #244 -- #242's record (`20260829-102912-b3e943f.md`) found that
  `sim/lib/simenv.sh::simenv_apply_omp_pin`'s `OMP_NUM_THREADS=1` pin makes
  **no measurable difference** to ngspice-46's own thread count for
  `sim/supply-sensitivity`'s closed-loop lock deck, even though the identical
  mechanism is confirmed working (~44x wall-clock) for #146's
  `mc-cp-mismatch` charge-pump-only deck on the same binary. #244 asks why,
  and asks for an effective mechanism if one exists.

  **Root cause (live-confirmed, not the `strings`-symbol hypothesis #242
  floated)**: this ngspice-46 build's OpenMP runtime honors the standard
  `OMP_NUM_THREADS` environment variable for the `mc-cp-mismatch` deck, but
  for the much larger closed-loop deck the live thread count stays at 8
  regardless of `OMP_NUM_THREADS` -- consistent with the OpenMP spec's own
  distinction between `OMP_NUM_THREADS` (seeds the `nthreads-var` internal
  control variable, which a program's own in-process `omp_set_num_threads()`
  call can reassign for a specific parallel region afterward) and
  `OMP_THREAD_LIMIT` (seeds `thread-limit-var`, a hard ceiling on live thread
  count that no in-program call can exceed). Empirically, setting
  `OMP_THREAD_LIMIT=1` **does** cap this deck's live thread count to 1, where
  `OMP_NUM_THREADS=1` alone does not -- this is the effective mechanism #244
  asked for. `sim/lib/simenv.sh::simenv_apply_omp_pin` now exports both
  variables, independently defaulted (an explicit caller-set value for either
  one is still always respected and never overridden), so this is a
  centralized fix, not a per-campaign one -- `sim/supply-sensitivity`'s and
  `sim/mc-cp-mismatch`'s calls to `simenv_apply_omp_pin` did not need to
  change.

  A `.spiceinit`/`set num_threads=N` ngspice-level directive (#242's original
  hypothesis) was investigated and **not found**: `strings` on this build
  shows only OpenMP-runtime symbol names (`omp_set_num_threads`,
  `omp_get_num_threads`, the compiler-emitted `num_threads` clause metadata)
  and no `.options`/`set`-style literal comparable to known real ngspice
  option names (`TNOM`, `GMIN`, etc., confirmed present in the same `strings`
  output as a positive control). This build exposes no ngspice-level thread
  control beyond the two standard OpenMP environment variables.

- **Methodology / criteria / limitations**:
  - **Isolated single-invocation probing** (`ngspice -b -o <log> deck.sp`,
    bypassing `run.sh`'s own `xargs -P` fan-out, matching
    `20260829-102912-b3e943f.md`'s methodology): thread count read from
    `/proc/<pid>/status`'s `Threads:` line, sampled every 0.2-1s across each
    process's life (not a single snapshot), cross-checked against `ps`'s
    `%CPU`/`TIME`/`ETIME` columns as a second signal (a genuinely
    single-threaded process cannot sustain `TIME` growth faster than
    `ETIME`, i.e. `%CPU` bounded near 100%; a truly 8-threaded process can
    reach several hundred percent).
  - **Candidate mechanisms tested on the closed-loop deck** (baseline / no
    env override; `OMP_NUM_THREADS=1`; `OMP_THREAD_LIMIT=1`; both together):
    only `OMP_THREAD_LIMIT=1` (alone or combined with `OMP_NUM_THREADS=1`)
    reduced the live thread count from 8 to 1. `OMP_NUM_THREADS=1` alone
    reproduced #242's finding exactly (`Threads: 8`, confirmed via
    `/proc/<pid>/environ` that the variable really was present in the
    process's own environment).
  - **Integration-level re-check**: after updating
    `sim/lib/simenv.sh::simenv_apply_omp_pin` to export both variables,
    sourced the real (unstubbed) function against the real `ngspice-46`
    binary on `PATH` (not `SIMENV_NGSPICE_LDD_OUTPUT`-stubbed, which is only
    used by the unit tests in `sim/lib/test_simenv_omp_pin.sh`) and confirmed
    it exports `OMP_NUM_THREADS=1` and `OMP_THREAD_LIMIT=1`, then launched
    the closed-loop deck under that exact environment and sampled
    `/proc/<pid>/status` every second for the first 5 seconds (`Threads: 1`
    every sample) and again once more at `t=737s` into the same run
    (`Threads: 1`, `ps` showing `TIME 00:09:46` against `ETIME 760s`, i.e.
    ~77% sustained CPU -- consistent with one active thread experiencing some
    scheduler contention from the host's other tenants, not with 8 threads).
    The run was killed at that point (>12 minutes elapsed, no error in its
    log, op-point/transient output still being written normally) rather than
    run to completion -- per the Guardrails on this issue ("not a
    `sim/supply-sensitivity` campaign re-run for its own sake") and this
    host's current non-idle state, a full wall-clock completion number was
    not pursued. The single-invocation, fully-serialized (1-thread) run
    appeared to be taking noticeably longer than either of
    `20260829-102912-b3e943f.md`'s two (falsely-pinned-but-actually-8-thread)
    runs -- unsurprising given that record's own "user/real ratio ~5-6x"
    finding, which shows genuine multithreaded speedup was happening on this
    deck even though `OMP_NUM_THREADS` wasn't the lever controlling it. This
    is expected and does not weaken the fix's value: the fix's target is
    **campaign-level** throughput (avoiding `SIM_JOBS` external processes
    each squaring against ngspice's own internal thread count, #58's
    original failure mode), not single-isolated-process wall-clock, which a
    single-invocation test cannot demonstrate either way.
  - **Compatibility check against #146's precedent** (per this issue's own
    Guardrails: "must not silently break" #146, though re-litigating its
    finding is out of scope): probed the `mc-cp-mismatch` deck under
    `OMP_NUM_THREADS=1`, `OMP_THREAD_LIMIT=1`, and both together. That deck
