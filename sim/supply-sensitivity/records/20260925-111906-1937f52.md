- **Methodology / criteria / limitations**:

  All of it is implemented in
  `sim/supply-sensitivity/testbench/trim_msb_audit.py`, whose pure functions
  are unit-tested against analytically-known inputs in
  `sim/tests/test_supply_sensitivity_trim_msb_audit.py`. Nothing below is

  `corners/20260925-111906-1937f52/trim_msb_audit.csv` and

  **The defect, stated once.** `design/lock_detector.sym` places the `LDT3`
  pin at symbol-relative `(−70, −60)`, above `UP`, while `LDT0`–`LDT2` sit at
  `(−70, +20/+40/+60)`, below `DN`. `design/pll_top.sch` instantiated `XLD` at
  `(300, 900)` and placed all four trim labels as if the run continued below
  `LDT2` — `y = 920, 940, 960, 980`. Three landed on a pin; `l_XLD_LDT3` at
  `(230, 980)` landed on empty canvas, and the real pin at `(230, 840)` was
  left open. xschem exported the open terminal under an auto-generated name,
  so `.subckt pll_top` declared an `LDT3` port that nothing inside it read and
  `XLD`'s eighth argument read `net1`. **The detector therefore saw
  `code & 0b0111` at every code**: the eight codes 8…15 were unreachable, and
  a deck programming one of them ran at the code eight below it.

  **Two independent readings, and agreeing is what makes the conclusion
  safe.**

  - **A — the node dump. Direct, and decisive on its own.** Each log prints
    the level of the `ldt3` pad *and* of `xdut.net1` in the same DC operating
    point table. A pad at the rail beside a stray net at 0 V is the defect
    stated by the simulator itself. The script reports `unknown` rather than
    `no` where the pad is *low*, because a low pad and a floating net are
    indistinguishable and a row that cannot show the defect must not be
    counted as showing it.
  - **B — the window comparison. Behavioural, and it discriminates.** The
    flag asserting *is* the detector comparing its own window against the
    offset the loop stands off. So each point's observed flag can be read
    against the `t_win` the committed code map measures at the **same**
    (bundle, temperature, supply) for the programmed code and for the
    effective one. Where the two predictions differ, the observation says
    which code ran.

  **The predicted direction is the source table's own one-sided bound, not a
  new rule.** `window_crossing.csv`'s header states it: *the observable assert
  window is never SMALLER than `t_win`*, so `t_win > |phi_b|` predicts an
  assert. Below the offset the bound predicts **nothing** — the observable
  window could still be above it — so the script writes `unpredicted`, never
  "predicts no assert". Converting a bound into a claim in that direction is
  the one error that would let this record overstate its own finding.

  **Limitations, stated rather than buried.**

  - **`t_win` is corroboration from a different campaign at a different
    `f_ref`** — `sim/lock-window-trim` drives `delaywin_3v3` directly at
    f_ref = 25 MHz; this loop runs at 12.5 MHz. `window_crossing.csv`
    deliberately keeps `t_win` out of its verdict for exactly that reason, and
    so does this record: reading B is used to *corroborate* reading A and to
    *predict* what a re-take would show, never to assert a verdict a loop did
    not produce.
  - **The predicted margin at the affected cell is small.** At code 11 the
    map's edges sit **+0.068 / +0.047 ns** above the settled offset (5.5 % /
    3.8 %). A prediction with that margin, carried across an `f_ref` change,
    is a reason to re-take the cell — which is what this record asks for — not
    a substitute for having re-taken it.
  - **This record measures no window and no offset.** It re-reads committed
    ones. The only thing it establishes by direct observation is *which code
    the detector saw*.
  - **It supersedes nothing and retracts nothing.** Per `sim/README.md`'s
    append-only rule, `20260920-180604-0f91a9b` stands exactly as taken: it is
    a true record of what that deck produced. What was wrong is the
    *configuration it was described under*, and this record is the correction
    of that description.
  - **No re-take is performed here.** The re-take needs a fresh closed-loop
    transient on the fixed netlist, and it is owed — see Result section 4.

- **Result**:

  ### 1. Which code each committed point actually ran at

  Ten logs audited; **5 of 10 programmed a code the detector never saw**, and
  all five are the `ff`/27 °C cell.

  | Log | programmed | pad `ldt3` | `xdut.net1` | MSB reached cell | detector saw |
  |---|---|---|---|---|---|
  | `f100_ff_27c_2.97v` | 11 (`1011`) | 2.97 V | 0 V | **no** | **3** (`0011`) |
  | `f100_ff_27c_3.30v` | 11 (`1011`) | 3.30 V | 0 V | **no** | **3** (`0011`) |
  | `f100_ff_27c_3.63v` | 11 (`1011`) | 3.63 V | 0 V | **no** | **3** (`0011`) |
  | `f100x_ff_27c_2.97v` | 11 (`1011`) | 2.97 V | 0 V | **no** | **3** (`0011`) |
  | `f100x_ff_27c_3.30v` | 11 (`1011`) | 3.30 V | 0 V | **no** | **3** (`0011`) |
  | the five `typical`/−40 °C logs | 7 (`0111`) | 0 V | 0 V | unknown | **7** (`0111`) |

  `f100x_` is the **same** steady-state deck re-run longer by `run.sh`'s
  settling escalation, not a second bench; the `supplied_row` column of the
  CSV marks which of the two produced each committed `supply_steady.csv` row,
  so an escalated re-run and the short run it replaced are never counted as
  two measurements.

  **The `typical`/−40 °C cell is unaffected, and the reason is arithmetic, not
  luck.** The rule selects code 7 for the `typical` bundle; 7 has its MSB
  clear, so `7 & 0b0111 = 7`. Its three points ran at exactly the code the
  record states. The audit reports them as `unknown` rather than `yes`
  because a log whose pad is low carries no evidence about the wire — but the
  *code* is right either way, which is the fact the record's verdict rests on.

  **Blast radius, enumerated.** `grep -rl 'ldt3_code=1' sim/*/corners/*/`
  returns exactly these five logs across the whole repository, and
  `grep -rl 'xdut.net1' sim/` returns exactly the ten logs of this one record.
  `sim/lock-detector` and `sim/lock-window-trim` drive `lock_detector` /
  `delaywin_3v3` directly rather than through `pll_top`, so no code they ran
  passed through the missing wire. **No other committed record in this
  repository is affected.**

  ### 2. What the observation says about which code ran

  One of the eight `ff` points discriminates, and it is the one
  `window_crossing.csv` reports.

  | Point | \|phi_b\| (ns) | `t_win` at 11 (r/f, ns) | predicts | `t_win` at 3 (r/f, ns) | predicts | observed |
  |---|---|---|---|---|---|---|
  | `ff`/27 °C/**3.63 V** | **1.2331** | 1.3015 / **1.2801** | **assert** | 0.9865 / **0.9721** | unpredicted | **did not assert** |
  | `ff`/27 °C/3.30 V | 1.0165 | 1.3631 / 1.3430 | assert | 1.0338 / 1.0209 | assert | asserted |
  | `ff`/27 °C/2.97 V | 1.0267 | 1.4428 / 1.4252 | assert | 1.0952 / 1.0849 | assert | asserted |

  At 3.63 V the two codes part company: code 11's window stands **above** the
  settled offset, so the bound predicts the flag asserts, and it did not.
  Code 3's window stands 0.25–0.26 ns **below** it, under which a non-assert
  is exactly what is expected. The behavioural reading therefore agrees with
  the node dump: **the loop ran at code 3.** The other two supplies are
  consistent with both codes and discriminate nothing, which is why they are
  reported and not counted.

  ### 3. What this does to the verdicts `spec/pll.md` cites

  `window_crossing.csv`'s verdict key, transcribed: DR-013 inferred
  **crossed** and the flag asserted → `confirmed`; inferred crossed and it did
  not → `refuted`; inferred **not-crossed** and it asserted → `moved`;
  inferred not-crossed and it did not → `confirmed`.

  | Cell | as recorded | standing now |
  |---|---|---|
  | `typical`/−40 °C/3.63 V, code 7 | `above`, **confirmed** | **stands.** Code 7's MSB is clear; the cell ran at the code the record states |
  | `ff`/27 °C/3.63 V, "code 11" | `at-or-below`, **confirmed** | **withdrawn as a statement about code 11.** It is a true observation *at code 3*, where `at-or-below` is what the map predicts. It says nothing about the rule-selected code |

  **The withdrawal is not neutral, and the record says which way it leans.**
  At code 11 the committed map puts the window **above** the offset, so the
  bound predicts an assert — which under the key above would make the cell
  **`moved`**, not `confirmed`: the window would be above the offset where
  DR-013 had it below. So DR-013 Decision 4's "(b)" item is **not discharged
  at this cell**, and the re-take may well move it rather than re-confirm it.
  This record does **not** assert that outcome — the margin is 3.8–5.5 % and
  the map is at another `f_ref` (see Limitations). It asserts that the
  question is open, which the source record's own numbers, read at the code
  that actually ran, no longer close.

  **What is NOT affected, and why.** `design/pll_top.sch` note 3 and DR-002
  Decision 4 make the lock detector a **passive monitor**: it taps `UP`/`DN`
  and nothing in it drives a loop node. `XLD`'s `LOCK` output leaves `pll_top`
  as a port and `VWIN` is an internal net with no reader. So the trim code
  cannot have moved this record's frequency, static-phase, control-voltage,
  current or power columns — only the detector's own `lock_lvl_v` and the
  crossing table derived from it. The source record's criterion-1 and
  criterion-2 `FAIL:phi` verdicts at `ff`/27 °C are graded against the
  ratified `<= 1 ns` static-phase bound, not against the detector, and stand
  untouched.

  ### 4. What is owed, and who owns it

  A closed-loop re-take of the `ff`/27 °C cell at `KWINTRIM=rule` on the
  **fixed** netlist — a fresh transient at each of 2.97 / 3.30 / 3.63 V, the
  3.63 V point being the one that carries the crossing verdict. It could not
  have been run before the schematic fix in this pull request: any
  `pll_top`-level run at a code with its MSB set would have repeated this
  defect silently.

  It is owed against **#437** (`loom:operator-only`), the declared
  trimmed-window **full-grid** re-run of this campaign, of which the `ff`/27 °C
  cell is a subset. That issue must be run on a netlist at or after this
  record's commit; a re-run taken on the pre-fix export would reproduce the
  same corruption at every point of the `ff` bundle. `run.sh`'s transcription
  of the rule maps `ss`/`all-slow` → 3, `fs` → 6, `ff`/`all-fast` → **11**,
  `typical`/`sf` → 7, so on the 45-point grid exactly one of the five bundles
  carries a code with its MSB set: **3 of the 15 (bundle, temperature) cells,
  9 of the 45 points**, all of them `ff`. The other four bundles' codes are
  all ≤ 7 and would run correctly even on the broken export — one reason this
  defect stayed invisible: the only committed campaign ever to program `LDT3`
  through `pll_top` at all is the source record, and only its `ff` cell
  carries a code the missing wire could corrupt.

  `design/lib/check-port-connectivity.sh`, added in the same pull request, now
  fails CI on any committed netlist that declares a top-level port nothing
  inside the subcircuit connects to, or that carries an xschem `net<N>` with a
  single connection. It reproduces this defect on the pre-fix
  `design/netlist/pll_top.spice` and passes on all seven post-fix netlists.
