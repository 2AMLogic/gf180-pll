# `divider_chain` block layout — DRC- and LVS-clean (issue #310)

Part 5, and the final part, of #295's `divider_chain` full-custom layout
decomposition (#306 leaf devices → #307 row cells → #308 `dff_tg_3v3` →
#309 `div23_cell` → **#310 block assembly**). This is the assembled block:
six `div23_cell` macro instances chained `VCO → CK1 → … → CK6`, the
termination/one-hot-mux glue logic, and the `XFRT` retiming flop — **452
transistors**, wired per `design/netlist/divider_chain.spice`'s own
`divider_chain` subckt.

Generated by `layout/pll_top/divider_chain/divider_chain.py`.

## What this is, and is not

This **is** a real, DRC-clean **and** LVS-clean 452-transistor block layout.
It **is not** a placed-and-routed-into-the-chip result: it is the block
standing alone, in its own coordinates. Its footprint is a serious floorplan
problem, stated in full below and in `PLL-FLOORPLAN.md` §5.1 rather than
absorbed.

**Not a vacuous pass.** The extracted netlist shows **226 `pfet_03v3` + 226
`nfet_03v3` = 452 devices**, all matched with correct W/L, across **71 named
top-level nets**. The extraction's own port names show the correspondence the
comparer found, net by net — e.g. `CKIN|VCO` (this block's `VCO` input
matched to `XD0`'s own `CKIN`), `CK1|CKIN|CKOUT` … `CK5|CKIN|CKOUT` (each
chain net matched to the driving instance's `CKOUT` *and* the receiving
instance's `CKIN`), `MI0|MODIN` … `MI4|MODIN`, `MO0|MODOUT` … `MO5|MODOUT`,
`MODIN|SEL5` (the sixth instance's modulus input tied to the `SEL5` port, per
the netlist's `XD5` line), `P|P0` … `P|P5`, and `VDD|VDD_DIV`. A merged or
mis-corresponded chain would show up precisely here.

### The reference netlist is the generated one, flattened — and why

`design/netlist/divider_chain.spice` (generated by `design/netlist.sh` from
`design/divider_chain.sch`) is this block's Acceptance-Criteria reference.
`divider_chain.reference_netlist()` is a **flattened re-expression** of it,
not a re-derivation: every device, size and connection traces to that file's
own `.subckt` bodies via each referenced module's own already-independently-
stated `reference_netlist()` (`div23_cell`, `nor2_3v3`, `inv_3v3`,
`nand2_3v3`, `nand3_3v3`, `inv2x_3v3`, `dff_tg_3v3`).

**A first attempt used the generated hierarchical file directly and failed
LVS with total mismatch** — every net and device unmatched. gf180mcu's LVS
deck (`align`) does not flatten a hierarchical schematic to match a flat
layout: it corresponds circuits by *name*, and this block's GDS has no named
sub-circuits once flattened. Flattening the reference the same way makes the
comparison the flat-vs-flat case `div23_cell.py`/`dff_tg_3v3.py` already
prove out.

### Every routed net is labelled, and that was necessary

Flattening the reference alone was **still** not enough. Confirmed
empirically during bring-up: two chained `div23_cell` instances with no glue
logic LVS-match cleanly; the same construction at six instances reproduces
the full-design mismatch, while DRC stays clean throughout. That isolates the
cause to the comparer's topology-only graph matching — six structurally
identical macro copies (each already internally repetitive: 2× `nand2_3v3`,
2× `inv_3v3`, 2× `dff_tg_3v3`) is enough symmetric structure that
connectivity alone does not always yield the correct correspondence, even
though the connectivity itself is correct on both sides (independently
confirmed by probing the reference's own net terminal lists).

The fix was to give the comparer's name-based hint matching enough to work
with: `build()` labels **every** net in its own `nets` dict — all 71 — not
just the 17 subckt ports, each with the exact name `reference_netlist()`
gives it (both derive from the same tables). Each instance's own
*internal-only* nets stay unlabelled, exactly as in `div23_cell`'s own
independently-LVS-clean standalone build.

This is a limitation of the comparer on a highly repetitive design, **not a
`klt` gap** — it is gf180mcu's own LVS deck driving KLayout's native
`NetlistComparer`, with `klt` not in the path at all.

## Six identical `div23_cell` instances (#295's acceptance criterion)

#295 requires the six instances stay byte-identical, so a future
TSPC/E-TSPC single-cell swap remains a one-symbol substitution rather than
six independent redraws that can silently drift.

`build()` builds `div23_cell` **once**, writes it to one scratch GDS, and
places six `klayout.db.CellInstArray` references translated into a row —
then flattens the top cell (`top.flatten(-1, True)`), the same technique and
the same reason `layout/harness/cell.py` uses: the decks then compare a flat
layout against a flat reference, with no subcircuit-correspondence question
in the way.

Because the hierarchy is gone by the time anything can inspect it, the
property is verified **geometrically** rather than by trusting the
`CellInstArray` call. `layout/tests/test_divider_chain.py`'s
`test_six_div23_instances_are_laid_out_identically` clips each instance's own
window out of the flattened top cell, translates it back to a common origin,
and XORs it against instance 0's, on every device layer:

| Layer | Polygons per instance | XOR vs. instance 0 |
|---|---|---|
| `comp` | 120 | empty (identical) |
| `poly2` | 60 | empty |
| `nplus` | 56 | empty |
| `pplus` | 60 | empty |
| `nwell` | 1 | empty |
| `contact` | 594 | empty |
| `metal1` | 240 | empty |

`metal1` is included and still exact because the block's top-level routing
fabric adds only metal2/via1/via2/metal3 above the instances, never metal1
inside them.

## `VDD_DIV` supply domain (#310's acceptance criterion)

`design/netlist/divider_chain.spice` names this block's supply `VDD_DIV`
throughout, and the layout carries **no other supply net at all**: every one
of the 452 devices — inside the six flattened `div23_cell` copies (whose
local `VDD` boundary pin is translated onto `VDD_DIV`) and in the glue logic
(whose periodic taps tie to `VDD_DIV` directly) — lands on one Metal1/2/3
fabric carrying only that name.

That makes the "never shares a segment with `VDD`/`VDD_VCO`" requirement true
**by construction rather than by inspection**: there is no `VDD` or
`VDD_VCO` net in this block for anything to merge with.
`test_divider_chain.py`'s `test_the_only_supply_net_is_vdd_div` asserts it
over every device terminal in the flattened reference, and the extracted
netlist above confirms the same on the layout side (`VDD|VDD_DIV`, `VSS`, and
no third supply among the 71 ports).

## `XFRT` placement (`PLL-FLOORPLAN.md` §4)

`XFRT` is one `dff_tg_3v3` (#308) retiming `DIVOUT` on `VCO` to produce `FB`.
It is placed **last in the glue row**, immediately after the `XMNO`/`XIDO`
output stage that generates `DIVOUT` — so the `DIVOUT → XFRT.D` run is the
shortest in the block, and `FB` exits at the block's own right edge
(`FB @ x = 2608.31 µm`, against the block's 2634.28 µm right extent, i.e.
within 26 µm of the boundary) rather than being routed back across the chain.
This keeps the `CLK → FB` path short, which §4 requires because `XFRT`'s
clk→Q skew (2.388e-10 s worst-direction, #15's record) is additive to the
PFD's static-phase-offset budget term (term 4, ±3 ns).

**Stated limit of this claim:** short and boundary-adjacent is verified;
"symmetric with the PFD's own `FB` input trace" is **not** verified here and
is not claimed — the PFD/CP block has no assembled layout yet, so there is no
counterpart trace to be symmetric with. That comparison belongs to the
top-level assembly pass, once `pfd_cp` lands real geometry.

|---|---|

| Devices | 452 (6 × 60 in `div23_cell` instances + 92 glue logic) |
| Area per transistor | ≈547 µm² |

| Pin | (x, y) µm | | Pin | (x, y) µm |
|---|---|---|---|---|
| `VCO` | (68.12, 0.94) | | `SEL0` | (2114.11, 10.64) |
| `P0` | (1.62, 2.82) | | `SEL1` | (2149.16, 10.64) |
| `P1` | (353.76, 2.82) | | `SEL2` | (2184.21, 10.64) |
| `P2` | (705.90, 2.82) | | `SEL3` | (2219.26, 10.64) |
| `P3` | (1058.04, 2.82) | | `SEL4` | (2254.31, 10.64) |
| `P4` | (1410.18, 2.82) | | `SEL5` | (1760.92, 4.70) |
| `P5` | (1762.32, 2.82) | | `DIVOUT` | (2517.96, 1.07) |
| `VDD_DIV` | (4.42, 11.37) | | `FB` | (2608.31, 1.07) |
| `VSS` | (5.12, 0.51) | | | |

**This footprint does not fit the chip.** `PLL-FLOORPLAN.md` §5 budgeted
"divider chain + lock detector" at 0.0038–0.0052 mm² (a ROM estimate made
when neither block had a physical view). This block alone is **0.2471 mm²** —
1.7× the entire 0.15 mm² die target — and at 2634 µm wide it is roughly 4×
the rest of the floorplan skeleton put together. §5's own "fail-loud
condition for a future pass" asks for exactly this to be stated rather than
rounded away, and `PLL-FLOORPLAN.md` §5.1 now does so, with the full
re-derived budget arithmetic (0.4283 mm² after top-level overhead, ≈2.9×
over).

**Where the area goes, measured:**

- **The block is one row.** Six `div23_cell` instances (332.14 µm each, from
  #309) plus 46 glue columns placed side by side, so the block width is the
  sum of every sub-cell's width. The six instances contribute 75,329 µm² of
  the 247,148 µm² total.
- **≈57 % of the block's height is routing, spanning the full width.** The
  shared per-net Metal2 track band is 71 nets × 0.75 µm pitch ≈ 53 µm of the
  93.82 µm total height, and every track spans the block. That is ~140,000
  µm², the single largest term.

**Why the #324-style fold is not the fix here.** Folding the VCO's
band-select mirror into two banks worked because that block's height was free
(the skeleton's height was set by `LOOP_FILTER`). Here each new row wants its
own track band, so a naive fold trades width for height at roughly constant
area. A real reduction needs the routing fabric to change (localized per-row
tracks, or a channel router rather than one-global-track-per-net) and/or the
diffusion-island-per-device convention `vco/primitives.py` documents. That is
materially larger work than #324 and is tracked separately, not attempted in
#310 — which is a DRC/LVS-clean geometry claim, and that claim is unaffected.

## `DIVIDER_LOCK` reconciliation — closed by this issue

#296 (`lock_detector`, 119.3 × 62.6 µm) and #295/#310 (`divider_chain`) each
deferred sizing the shared `DIVIDER_LOCK` region to whichever landed second.
#296 landed first (2026-09-08, PR #311), so #310 performs it:

- `layout/floorplan/skeleton.py`'s `DIVIDER_LOCK` is now **2650.28 × 212.42
  µm**, sized to contain both blocks' real footprints — the 90 × 50 µm
  placement-plan estimate is superseded and should not be cited again.
- The two blocks are **stacked with a full `DOMAIN_SPACING` (40 µm) gap**,
  not abutted: they are on different supply domains (`VDD_DIV` vs. `VDD`,
  §2), so sharing the region buys signal adjacency, never a shared supply
  segment. Confirmed in both generators — `divider_chain.py` draws no `VDD`
  net, `lock_detector/build.py` draws no `VDD_DIV`.
- The region is placed above every other block, clearing the VCO's 15 µm
  guard-ring keep-out.
- `layout/tests/test_floorplan_skeleton.py` asserts containment,
  non-overlap, the domain gap, and the keep-out clearance, so the
  reconciliation is a checked invariant rather than a prose claim.

## Reused from #306–#309 (issue's own acceptance criterion)

The six `div23_cell` instances are #309's macro **unmodified** — one
`div23_cell.build()` result, placed six times by translation. `XFRT` is
#308's `dff_tg_3v3` composite. The glue logic is drawn from the same
`nor2_3v3`/`inv_3v3`/`nand2_3v3`/`nand3_3v3`/`inv2x_3v3` `COLUMNS`/device
tables #307 ships, with the same per-column net-offset and periodic-tap
geometry `div23_cell.py` already proved DRC-clean for this leaf-cell family
(imported from that module, not re-derived). No device geometry (W/L) is
re-derived or hand-copied anywhere; only net names are translated per
instance.

## Friction-protocol note

**No new `klt` capability gap was hit assembling this block**, so none is
filed (per CLAUDE.md: describe a real gap, or file nothing). The existing
gaps already cited by #306/#308/#309 (`2AMLogic/klayout-tools#1575`,
`klt gen`/`klt gen-compose` failing gf180mcu's real signoff deck rule
families; klayout-tools#54, no `klt lvs` verb) still cover why this module
draws direct `klayout.db` geometry and runs the PDK's own decks.

The one genuinely new difficulty here — the LVS comparer's inability to
resolve six structurally identical macro copies from topology alone — is
**not** a tool gap in `klt`: `klt` is not in that path. It is gf180mcu's own
LVS deck driving KLayout's native `NetlistComparer`, and the fix belongs in
this design's own labelling (applied in `divider_chain.py`), not upstream.
