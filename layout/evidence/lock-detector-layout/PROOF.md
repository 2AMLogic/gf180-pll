# lock_detector block layout — DRC run (issue #296)

Real, transistor-level layout for the `lock_detector` block (phase-error
window comparator: `ERR = XOR(UP, DN)`, a 4-stage RC-style delay window
producing `ERRD`, `WIDE = ERR . ERRD` gating, a weak-pull-up/gated-pull-down/
MOS-cap `VWIN` integrator node, and a Schmitt trigger producing `LOCK`),
generated by `layout/pll_top/lock_detector/build.py` and checked with

```
python3 layout/run_pv.py drc <gds> --top <cell> --run-dir <dir>
```

against the gf180mcu PDK's own foundry DRC deck (not `klt drc`'s curated
subset — see `layout/README.md`'s "Why this isn't `klt drc`" section).

## What this is, and is not

Every device is transcribed directly from `design/netlist/lock_detector.spice`
(itself generated from `design/lock_detector.sch` + the leaf-cell schematics
it instantiates — `xor2_3v3.sch`, `delaywin_3v3.sch`, `nand2_3v3.sch`,
`inv_3v3.sch`, `schmitt_3v3.sch`) — see `layout/pll_top/lock_detector/devices.py`.
All transistors are `nfet_03v3`/`pfet_03v3` (DR-002 Decision 3's 3.3 V
thick-oxide flavour). This is a **DRC-clean geometry claim only** — LVS
(netlist-match against `design/netlist/lock_detector.spice`) is not run here
and is not claimed; `layout/README.md` documents why this flow's LVS gate
uses the PDK's own `run_lvs.py`, not `klt lvs` (no such verb exists yet,
tracked at klayout-tools#54).

**Supply domain.** Every net drawn here is `VDD`/`VSS` — there is no
`VDD_DIV` (or any other non-`VDD` supply) net anywhere in
`build_lock_detector()`, so there is no way for this block's own routing to
tie into the divider chain's separate `VDD_DIV` trunk, even though the two
blocks share `layout/floorplan/skeleton.py`'s `DIVIDER_LOCK` placement
region for physical adjacency only (`PLL-FLOORPLAN.md` §2).

**Passive-monitor claim.** This layout draws exactly the netlist above: two
inputs (`UP`, `DN`, read-only — nothing here drives them), two outputs
(`LOCK`, `VWIN`). No counter, no state machine, no feedback path into a loop
node is drawn or implied — matching `design/README.md`'s description of this
block.

## Friction

One `klayout-tools` capability gap was hit and filed generically (tool gap,
not this design) per `CLAUDE.md`'s friction protocol: the schematic's
always-on weak pull-up (`MUPW`, narrow-and-long by design, for a high channel
resistance) is narrower than `mos_array`/`diff_pair`'s `UNIT_MIN_W_UM`
contact-fit floor (0.42 um) — a real instance of the "use case for
narrower-than-contact-fit unit devices" klayout-tools#322's own triage
comment flagged as the trigger for a follow-up but deliberately left out of
that issue's scope. Filed as
[2AMLogic/klayout-tools#1574](https://github.com/2AMLogic/klayout-tools/issues/1574).
Worked around here with a hand-drawn dog-bone S/D terminal (widened contact
pad, unwidened shoulder against the gate edge, true schematic width under
the gate) in `layout/pll_top/lock_detector/primitives.py`'s `mosfet()`.

## Addendum (2026-09-09, issue #310): the `DIVIDER_LOCK` reconciliation is now closed

The "Results" section above records that reconciling `DIVIDER_LOCK`'s real
combined footprint was "left to whichever of #295/#296 lands second" and that,
#296 having landed first, "that reconciliation is still open". **It is no
longer open.** #310 (the final part of #295) landed the `divider_chain` block
and performed it. This addendum is appended rather than editing the statement
above, per this repo's append-only evidence convention.

- `divider_chain`'s own measured footprint is **2634.28 x 93.82 um**
  (0.2471 mm^2), against this block's 119.3 x 62.6 um — see
  `layout/evidence/divider-chain-layout/PROOF.md`.
- `layout/floorplan/skeleton.py`'s `DIVIDER_LOCK` is now sized to contain both
  real blocks (2650.28 x 212.42 um), stacked with a full 40 um
  `DOMAIN_SPACING` between them because they sit on different supply domains
  (`VDD` here, `VDD_DIV` there — consistent with the "Supply domain" note
  above). The 90x50 um placement-plan estimate is superseded.
- The combined region is a large overrun against `PLL-FLOORPLAN.md` section
  5's ROM budget; that is stated in full in that record's new section 5.1 and
  is dominated by `divider_chain`, not by this block.
