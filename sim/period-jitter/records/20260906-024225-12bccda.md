- **Methodology / criteria / limitations**:
  - WHERE THIS CAMPAIGN STANDS. Record 20260905-192724-a2ba48f established this claim's deterministic half at ONE nominal point (typical/27C/3.30V) and stated plainly that the mandated 45-point PVT matrix remained owed. This manifest now DECLARES that full matrix: 45 grid blocks, one per PVT point, each carrying its own control-node release voltage derived from committed VCO evidence by vstart_from_vco_record.py in this directory. What was owed is therefore no longer design work -- every remaining point is `python3 sim/run_corners.py period-jitter` with no --axis narrowing, i.e. compute. A run that narrows the declared grid says which points it ran and why, in this record's own Corner matrix field, on the same terms as any other PVT subset.
  - WHAT IS MEASURED, AND WHY IT IS A TIME-DOMAIN READ OF THE SAME MECHANISM sim/reference-spur MEASURES IN FREQUENCY. Once locked, the PFD fires both branches once per reference cycle for the reset-delay overlap, the charge pump's per-event charge asymmetry lands on the loop filter's C2, and the resulting Vctrl ripple phase-modulates the ring (design basis; sim/reference-spur's own methodology states it in full). sim/reference-spur (#145) reads that ripple out of the output SPECTRUM as a sideband; this record reads the identical physical ripple out of the output's TIME-DOMAIN edge sequence instead, which is the form spec/pll.md#period-jitter states its target in (percent of period, RMS) rather than dBc.
  - OPERATING POINT: IDENTICAL TO sim/reference-spur (#145), reused deliberately rather than re-derived. f_ref = 25 MHz, N = 6, f_out = 150 MHz, VCO band code 6, Icp trim code 0 (one unit leg, the Icp trim-code rule's required setting there). This is inside the ratified 1-25 MHz reference / 10-200 MHz output / N=4-64 space and is the highest output frequency one static band code holds across the whole PVT grid (sim/vco-tuning-range record 20260804-162735-72883fb) -- which is precisely why it, and not a different operating point, is the one that can be carried to all 45 corners at a single static band code. The per-PVT-point control-node release voltage is interpolated from that same committed VCO record by vstart_from_vco_record.py in this directory, one value per corner of the mandated matrix; that script re-checks the manifest against the record (--check) and regenerates the manifest fragment from it (--emit), and it loads its interpolation arithmetic from sim/reference-spur/testbench/vstart_from_vco_record.py rather than re-implementing it, so the two campaigns can never disagree about what the committed record says a corner's lock point is. Every static configuration bit in tb_period_jitter.sp is copied verbatim from sim/reference-spur/testbench/tb_ref_spur.sp, itself checked against sim/lib/pll_top_dut.sh's `cloop_divider_params`/`cloop_band_params`/`cloop_trim_params` by that directory's own check_config.sh.
  - WHAT A POINT OF THIS DECK COSTS, AND WHY THAT IS RECORDED HERE. A closed-loop transient at this campaign's 100 ps internal-timestep ceiling is expensive: sim/reference-spur's own methodology quotes 'thousands of CPU-seconds per point' for its longer 8 us run, and this deck is the same order. That cost, not any design uncertainty, is the only thing standing between this manifest and the full 45 points -- so a run that does not cover all 45 states the arithmetic in its Corner matrix field rather than leaving 'the grid remains owed' as an unquantified promise. Two things keep the per-point cost as low as it is. FIRST, the run length is not increased to accommodate the grid: the deck stays at `.tran 2n 5.7u 3.5u 100p` at every corner, because each corner is released at its OWN predicted lock point rather than at a common voltage -- across this grid that point spans 1.09-2.43 V, and at the loop's Icp/C1 = 14 mV/us slew a common release would spend tens of microseconds slewing before any measurement window could open. SECOND, the points are independent, so they are run in parallel across cores (`-j`); nothing about the numerical solution depends on that scheduling, since the per-point deck, options and tolerances are identical to the predecessor record's. Whether the release estimate was good enough at any given point is not assumed: it is gated per point by this manifest's ferr / fout / nmeas lock checks, and a point that fails them is reported as a failing point, never as a jitter number.
  - WHY A TRANSIENT AND NOT loop-dynamics' SMALL-SIGNAL ANALYSIS. The ripple is a nonlinear, periodic-steady-state effect (once-per-reference-cycle charge-pump event), exactly as sim/reference-spur's own methodology states; sim/loop-dynamics' linearized AC sweep cannot produce it and says so in its own Limitations field.
  - STEADY STATE, NOT LOCK TIME. The control node is released at `vstart` -- this corner's own predicted lock point, 1.09-2.43 V across this grid -- for the same reason sim/reference-spur does it: this campaign measures a STEADY-STATE property (the locked period sequence), not acquisition time (sim/lock-time, #12, owns that claim), and starting near the lock point reaches steady state for the least simulated time. The residual settling drift this leaves is not assumed away -- `ferr` is measured over a 1 us baseline (`ta`/`tb`) immediately before the measurement window and is reported as a lock-quality gate, exactly as sim/pll-top-smoke's and sim/reference-spur's lock criteria are, and `tie_*` de-trends the crossing sequence by its own least-squares line so a residual drift cannot be counted as jitter.
  - MEASUREMENT CRITERION: the reported RMS/pp period jitter and TIE come from every rising mid-supply crossing of `v(clk)` in the measurement window (`wa` to `wb`, 300 output cycles = 2.0 us at 150 MHz), linearly interpolated between the two straddling ngspice timepoints (sim/vco-tuning-range's `_numeric.py:crossings`, the same primitive sim/vco-tuning-range's jitter extraction and sim/reference-spur's TIE cross-check both use). Period jitter is the RMS/pp deviation of the per-cycle period sequence from its own mean; TIE is the RMS/pp deviation of the crossing times from their own least-squares line (removes any residual settling drift from being counted as jitter, the same reason sim/reference-spur's TIE path de-trends by a fit rather than a nominal period). `sim/tests/test_period_jitter_derive.py` replays a synthetic waveform of known jitter through this exact reduction path, off any simulator, before this record's own number is trusted.
  - RANDOM / NOISE-DRIVEN JITTER IS NOT MEASURED BY THIS RECORD -- A METHODOLOGY GAP, STATED HONESTLY. DR-002 Decision 5 (spec/decision-records/DR-002-draft-spec-scope-ratification.md) ratifies (status: proposed) a VCO-dominated transient-noise testbench plus a jitter-transfer argument through the closed loop as the intended method for the random component, and explicitly rejects an ngspice AC `.noise` analysis as unsupported for a free-running oscillator's phase noise on this flow. Before writing this deck, `.option TRANNOISE=1` was tried on ngspice-46 (this repo's pinned build) against a trivial R-driven-by-a-DC-source circuit: the resulting transient carried NO noise -- a bit-for-bit flat waveform across the whole run -- so this pinned build does not inject automatic device noise into a `.tran` analysis (or the syntax this build recognizes for it is not `.option TRANNOISE=1`; either way, nothing in this repo's flow demonstrates it working). ngspice DOES support an explicit `trnoise()` PWL source function (confirmed working, injecting a synthesized white/1-f voltage waveform) -- but turning that into a credible DEVICE-noise-EQUIVALENT number requires first calibrating the injected amplitude against a validated noise-PSD measurement of the VCO's dominant noise contributors (thermal + flicker in the current-starved ring's bias and switching devices), which is real, separately-scoped methodology development this record does not attempt. Per sim/README.md's own worked example for this exact scenario ('A recorded methodology gap instead of a number (#13)'), this record states the gap here rather than publishing an uncalibrated, not-credible random-jitter figure. No random/noise-driven period-jitter number is reported anywhere in this record.
  - SIMULATOR SETTINGS. `.tran 2n 5.7u 3.5u 100p` -- the fourth argument is the 100 ps ceiling on ngspice's INTERNAL timestep every campaign whose DUT contains the PFD inherits (sim/README.md, 'Closed-loop internal-timestep bound'), verified per point via `dt_int_mean`. `.option rshunt=1e12 itl4=200 reltol=1e-3 abstol=1e-13 vntol=1e-6` matches sim/reference-spur's/sim/pll-top-smoke's exactly, so this deck's converged solution is comparable with the other closed-loop campaigns'.
  - LIMITATIONS. (1) Random/noise-driven jitter is not measured -- see above; this record answers only the deterministic half of #13's claim. (2) Schematic-level: no layout parasitics, no supply or substrate coupling into the VCO rail beyond what design/pll_top.sch itself models. (3) The reference is ideal: no reference jitter, no duty-cycle error -- a jitter contribution from reference-clock imperfection is out of scope here by construction, matching sim/reference-spur's own stated limitation.
