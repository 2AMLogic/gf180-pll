- **Claim**: #65's remaining items 2-4 (execute the full 45-point PVT grid at
  N=4, N=16/64, and `sim/output-range`'s full grid) are all code-complete but
  unexecuted, per the issue's own Curator refresh. This record answers a
  question that turned out to block execution of item 2 outright: **does
  `sim/lock-time`'s `cold` condition (the 0.9 V control-node clamp release)
  actually run to completion at the compliant 100 ps internal-timestep

  corners spanning the full PVT extremes. **It is a methodology/testbench
  record, not a PVT campaign** — it does not itself deliver the full grid
  items #65 still asks for; see Limitations.

- **Methodology / criteria / limitations**:
  - **How the failure was found**: attempting `sim/lock-time/testbench/run.sh
    --check` (the nominal-corner `cold` debug point, N=4, 4 us window, 100 ps
    ceiling — i.e. exactly the deck #65's item 2 needs to run 45 times) failed
    every time with:
    ```
    doAnalyses: TRAN:  Timestep too small; time = 1e-09, timestep = 1.25e-22: trouble with node "vp4#branch"
    ```
    `t`=1e-9 s is not incidental: for N=4, `t_force` = `0.02/fref` =
    `0.02/20e6` = 1 ns exactly — the failure lands on the clamp-release
    instant to the printed precision. Reproduced identically (same failure
    line, same instant, only the reported offending branch name differing
    between `vp3`/`vp4` — cosmetic, LTE-dependent) across **three independent
    invocations** at the nominal corner: the original 4 us window, and a
    10 ns `SIM_WINCAP` truncation run twice. See
    `corners/20260801-162534-2a81927/typical_27c_3.30v_n4_cold_UNFIXED_crash.log`
    for the full log (144.5 CPU-s to the final `run simulation(s) aborted`,
    unaffected by host contention since the failure is deterministic, not a
    timeout).
  - **Root cause**: `tb_lock_time.sp`'s control-node release mechanism
    (documented in the deck's own header, needed because a bare `.ic
    v(vctrl)=...` does not survive VCTRL's well-determined DC operating
    point) is a voltage-controlled switch, `.model SWFORCE SW(Ron=10 Roff=1G
    Vt='vsup/2' Vh=0)`, driven by a control pulse whose rise/fall time was a
    **hardcoded 100 ps** — numerically identical to `#65`'s own 100 ps
    internal-timestep ceiling (`SIMENV_CLOSED_LOOP_TMAX`). A switch moving
    across an 8-order-of-magnitude resistance ratio (Ron=10 Ω to Roff=1 GΩ)
    inside a span exactly as wide as the integrator's own step ceiling gives
    ngspice at most ONE internal step to resolve the entire transition — the
    LTE controller cannot satisfy its local error estimate at that step size
    and keeps halving until it underflows (`1.25e-22` s), which ngspice
    reports as the transient having failed, not merely as a slow step.
    **This is a pre-existing testbench defect, newly exposed rather than
    newly introduced**: before `#75` landed the 100 ps ceiling (`#65`'s own
    prerequisite work), the ceiling defaulted to the *print* step
    (`1/(50*f_out)` = 250 ps for this campaign), giving the same 100 ps
    transition ~2.5 ceiling-steps to resolve instead of ~1 — apparently just
    enough to avoid the LTE failure, which is why no prior session (all of
    which ran at either the old 250 ps default or investigated only `relock`,
    never `cold`, at the compliant ceiling) ever observed this.
  - **Why only `cold`, not `relock`**: both conditions release through the
    identical switch/pulse mechanism, differing only in `vctrl_ic` (0.9 V vs.
    2.7 V). `relock` was independently observed (this session and
    `20260801-125545-f0770e7.md`'s own abandoned 100 ps arms before it) to
    run for hundreds of CPU-seconds without hitting this failure signature —
    slow from host contention, not crashing. This record does not fully
    explain the asymmetry (it would need internal PFD/CP node visibility this
    record's instrumentation does not have — see the open item below) but
    notes it plainly: whatever makes the 0.9 V release numerically stiffer
    than the 2.7 V release is corner-independent (see Result) but
    condition-dependent.
  - **The fix**: `vsctrl`'s pulse rise/fall time changed from a hardcoded
    `100p` to `'10*tmax'` — an expression tied to the SAME
    `SIMENV_CLOSED_LOOP_TMAX` parameter already threaded through both decks,
    not a second hardcoded constant that could drift out of sync with it.
    Ten ceiling-steps across the transition gives the LTE controller room to
    follow it. Applied identically to `sim/output-range/testbench/tb_output_range.sp`,
    which uses the byte-identical switch/pulse construction: that bench was
    **not observed to reproduce the crash** at its one checked point
    (`typical`/27C/3.30V, `lo` edge, `vctrl_ic`≈1.68V — nowhere near a rail,
    unlike `cold`'s 0.9V) before the fix landed, in an attempt abandoned
    incomplete after 34 CPU-s under this session's severe host contention
    (see Limitations) — not long enough to either confirm or rule out the
    same failure at that corner. The fix is applied there anyway on the
    strength of the shared root cause (identical model, identical transition
    width, identical ceiling), verified afterward at that same corner to
    still classify `--check` correctly (no crash, no `ERROR` row) under the
    fixed deck, though — per the same contention — that confirmatory run
    was also not run to full completion; see Limitations for exactly what is
    and is not established for `sim/output-range`.
  - **Fix verification, `sim/lock-time`**: re-ran the previously-crashing
    nominal corner, plus the two most extreme corners on the default 45-point
    grid (coldest+fastest process vs. hottest+slowest, both at their
    accompanying supply extreme), all `cold`, N=4, 10 ns truncated window.
    **All three completed cleanly — no `ERROR`, no `Timestep too small`** —
    see Result. `vctrl_final` at `t`=10 ns sits within 1.3 mV of the 0.9 V
    seed at every corner (the clamp has only just released; the loop has not
    had time to move VCTRL meaningfully yet, as expected for a 10 ns window
    against a 50 ns reference period), and the DN-branch guard (`#69`) reads
    PASS at all three, confirming the ceiling is still being honoured with
    the widened release transition.
  - **What this does NOT establish**: (1) whether the fix changes any
    ALREADY-COMMITTED `relock` result — not tested here; the mechanism is
    scoped to the exact `t_force` instant and a 900 ps-wider release
    transition inside a multi-microsecond window is not expected to move a
    converged `vctrl_final` measurably, but this is reasoning, not a
    same-session controlled-pair measurement (`#75`'s own precedent for why
    that distinction matters), and is flagged rather than assumed; (2) the
    transistor-level reason `cold`'s 0.9V release is numerically stiffer than
    `relock`'s 2.7V one — would need internal PFD/CP/VCO node visibility this
    record's `.measure`/`wrdata` instrumentation does not capture; (3) whether
    `sim/output-range` has ANY corner that reproduces the crash under the OLD
    (unfixed) deck — the one point checked did not crash in the 34 CPU-s it
    ran before this session's contention forced abandoning it, which is not
    enough evidence to conclude the campaign was never exposed, only that the
    fix is applied defensively rather than reactively there; (4) the full
    45-point PVT grid at any of N=4/16/64 for `sim/lock-time`, or the full
    45-point grid for `sim/output-range` — **both remain #65's open items,
    unexecuted by this record**, now with the added prerequisite that the
    execution attempt use the fixed decks.
  - **Limitations**: schematic-level, no parasitics; nominal-skew only; three
    corners, one condition, one N, all at a diagnostic 10 ns window (not a
    lock-time measurement); host contention (65-117 load average on a

    though still real, oversubscription ratio) prevented running either the
    `relock` fix-verification point or the `sim/output-range` fix-verification
    point to completion in this session — both were launched, both were
    killed incomplete rather than left as orphaned background processes (see
    below), and neither contributes a number to this record.
  - **A process-hygiene finding, unrelated to the timestep bug but worth
    recording**: this session's worktree, on claim, was found running SIX
    orphaned `ngspice`/`bash` processes left by a prior session's abandoned
    `#75`/`#83`-era "controlled pair" experiment (`tmax_pair`/`tmax_pair_short`,
    the 100 ps arms `20260801-125545-f0770e7.md` itself documented as "left
    running rather than killed" so "a subsequent session may find a completed
    log"). Their working directories had already been deleted from the
    filesystem while the processes still held them open (`lsof` resolved the
    open file descriptor; `ls`/`find` could not see the path) — i.e. they
    were guaranteed to produce nothing recoverable, running 3-4 hours purely
    as host-load noise. Killed at the start of this session. **Revises the
    precedent those two prior records set**: "leave it running for a future
    session" only works if that future session's own worktree survives
    untouched in the interim; a worktree that gets reset (as this one needed,
    being 12+ commits stale) silently orphans anything still running inside
    it. This session killed its own two incomplete confirmation runs
    (`relock` fix check, `sim/output-range` fix check) explicitly rather than
    leaving them, to avoid repeating that outcome.
