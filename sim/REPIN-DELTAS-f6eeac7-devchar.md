# Re-pin deltas: device-characterization records under open_pdks `f6eeac7`

`sim/` evidence is append-only, so re-qualifying a frozen reference record
after a PDK pin changes mints a *new* record and names the old one in
**Supersedes** (`sim/README.md`, "Status / supersession language"). That
convention records *that* a re-run happened; it does not say *how much the
numbers moved*, which on a re-qualification is the whole finding. This
document is that missing half for the four benches re-run in #825 — the
device-characterization group of the #790 re-qualification, itself the
re-qualification half of the #788 fleet re-pin
(`c6d73a35f524070e85faff4a6a9eef49553ebc2b` → `f6eeac7dad085ffcc829ccfd721f7b4ce39edcf7`,
pinned by #789).

Every table below is generated from the two committed records by
`sim/lib/record_delta.py` and is reproducible from the tree alone; the exact
command sits above each one. Nothing here edits a record.

## The simulator moved too, and it is the one that moved the numbers

The fleet re-baked ngspice along with the PDK, so these records differ from
their predecessors in *two* variables at once (`c6d73a3` → `f6eeac7` and
ngspice-42/46 → ngspice-47) plus host OS and execution backend. #825's own
edge-case note and the 2026-11-13 operator ruling both flag that the tables
therefore mix PDK and simulator effects.

They need not stay mixed. `/usr/bin/ngspice` on a dispatch worker is
ngspice-42 — the exact version the `devchar-*` predecessors ran — so a
**single-corner local run** (which the host rules allow, and which spends no
fleet budget) pins the PDK as the only changed variable:

```bash
PATH=/usr/bin:$PATH SIM_NGSPICE_BIN=/usr/bin/ngspice \
  python3 sim/run_corners.py <slug> \
  --corners typical --temps 27 --supply-tol 0 --no-write --backend local -j 1
```

Result at `typical_27c_3.30v`, against the superseded record's own row for
that corner:

| campaign | measurements compared | identical under `f6eeac7` + ngspice-42 | differing |
|---|---|---|---|
| `devchar-cp` | 128 | 128 | 0 |
| `devchar-passives` | 123 | 123 | 0 |
| `devchar-delay` | 34 | 34 | 0 |

Identical to the last printed digit, in all three. **The PDK re-pin is a
bit-for-bit no-op on this bench group**; every residual difference in the
tables below is ngspice-47. (`harness-selftest` needs no probe: its recorded
re-run is already bit-identical to its predecessor across all 63 corners, so
neither variable moved it.)

That is a one-corner result, not a grid, and it is stated as one — it
establishes the attribution at the nominal corner, not at every corner. It is
offered as evidence, not as a substitute for the grids above.

### The one real movement: moscap leakage under ngspice-47

`devchar-passives`' whole non-zero delta is a single effect. The four
**MOS**-cap topologies (`cn`, `cnb`, `cp`, `cpb`) go from an identically-zero
`leak_*` to about **−0.9 nA** of residual branch current during the 3.63 V
hold, at every corner. Because `imin_*` is read in the same window, that
offset propagates arithmetically into `imin_*`, `dmin_*` and hence
`cvr_* = dmax/dmin` — which is exactly the 0.35 % column above, and the only
reason that column is not also at the ppm level. Every **MIM**-cap topology
(`m10`/`m15`/`m20`, `l10`/`l15`/`l20`) is unchanged to within attoamp solver
noise.

The ngspice-42 control probe above returns `leak_cn = leak_cnb = leak_cp =
leak_cpb = 0` under `f6eeac7`, so this is the simulator, not the models.

This matters beyond these rows, because the nonlinear moscap family is
precisely what #153 is about, and `--check-env`'s current ngspice-47 warning
tells a reader that "a flat, top-level instantiation (e.g.
`sim/devchar-passives`) is unaffected and runs on either version". On the
evidence here that is true of *failure* and false of *values*: the flat deck
does not fail, but ngspice-47 returns a different leakage number for the same
device. Filed as **#932** so the guidance and the measurement agree. Note what
it is not: no result here moved past a stated tolerance and no verdict
flipped, so #932 is the ngspice-47 follow-up this measurement surfaced, not
the "moved past tolerance" issue #825's third criterion asks for.

The conclusion of the campaign that cites these records is untouched: it rests
on the MIM family's C–V linearity and density (`spec/pll.md#area`,
`spec/decision-records/DR-042`), and the MIM rows did not move.

## Per-bench tables

`limit` is the bound the record itself states for that measurement (`—` where
it states none). `max rel delta %` is relative to the superseded record's
value; a measurement whose old value is zero contributes to the absolute
column only, which is why the moscap `leak_*` rows above read `0` there.
