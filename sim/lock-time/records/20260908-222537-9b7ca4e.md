- **Methodology / criteria / limitations**:
  - **The harness's own window-extension ceiling (a finding in its own
    right)**: #284's Curator guidance suggested re-running "at several
    multiples" of `relock`'s base window via `SIM_WINCAP`. Attempting that
    surfaced a real constraint in `run.sh`'s `run_one`: `tstop=min(80/fref,
    wincap)` -- the 80-reference-period figure is NOT itself overridable by
    `SIM_WINCAP`, which can only *shorten* `tstop` below it, never lengthen
    past it. `cold`'s own default cap (`4e-6*n/4`) already equals exactly
    80 reference periods at every N; `relock`'s default cap (`2e-6*n/4`) is
    exactly HALF of that same ceiling. So the maximum extension `SIM_WINCAP`
    can ever deliver for a `relock` row, at any N, is a **2x** widening (40
    -> 80 reference periods) -- never the "several multiples" #284's
    guidance envisioned, without a `tb_lock_time.sp`/`run.sh` change (out of
    scope here: #284 marks both read-only unless a genuine deck bug turns
    up, and this is a deliberate design choice, not a bug). Verified
    directly: `SIM_WINCAP=3.2e-5` (32us) requested against this corner's
    N=4 `relock` row produced a deck with `.param tstop=4e-06` (4us, not
    32us) -- see the committed logs' own `.param` lines. This record's
    "extended" run is therefore the full 2x extension the existing
    infrastructure can deliver, not an arbitrarily long one; deeper
    conclusions below lean on waveform-level reasoning (the Acceptance
    Criteria's alternative method) rather than on an even-longer window.
  - **Baseline reproduction** (`run.sh --one typical -40 2.97 4 relock`, no
    `SIM_WINCAP`, default 2us/40-reference-period `relock` window):
    `vctrl_final` = 2.41668 V, `dn_lvl` = 2.08148 V, `lock_at_end` =
    8.8865e-08 (near zero -- not locked). Matches
    `20260831-052456-effc505.md`'s own row for this corner (2.417 V / 2.08 V
    at that record's printed precision) -- confirms this is a genuine
    reproduction of the same measurement, not a different setup.
  - **Extended run** (`SIM_WINCAP=3.2e-5`, actual `tstop` clamped to 4us/80
    reference periods per the ceiling above -- a 2x extension of the
    baseline window): `vctrl_final` = 2.42022 V, `dn_lvl` = 1.71108 V,
    `lock_at_end` = 4.24277e-09. **Net movement over the additional 2us: only
    +3.54 mV**, and in the WRONG direction relative to this corner's own
    measured lock point (below).
  - **Waveform-level trend** (`vctrl`/`up`/`dn`/`lock`/`vwin`, the fragment's
    existing instrumentation; full-resolution CSVs -- 20497 rows/2us,
    40977 rows/4us at the campaign's 100ps internal-timestep ceiling -- were
    generated and read directly for this analysis but are NOT committed at
    full resolution, per `sim/README.md`'s "Waveform rule" and its "few MB"
    guidance; a 10x-decimated baseline CSV and a 20x-decimated extended CSV
    are committed instead, ~330 KB each, preserving the same trend visible
    at full resolution): `vctrl` falls quickly from the 2.7V clamp-release
    value to ~2.40V within the first ~1-1.5us (~20-30 reference periods),
    then **plateaus**: 200ns-binned `vctrl` averages stay inside
    [2.400V, 2.406V] -- a 7 mV band -- continuously from t=1.7us to t=3.9us
    (44 reference periods, more than half of even the extended window).
    Quantified: the initial acquisition slope (t=[0,500ns]) is
    **-0.496 V/us**; the plateau-region slope (t=[1.7,3.9]us) is
    **+0.0029 V/us** -- about **170x smaller in magnitude, and the OPPOSITE
    sign**. This is not "slowing down while still heading the right way";
    it is a near-total stop, drifting slightly the wrong way.
  - **Cross-corner context, already-committed, not new evidence** (cited,
    not re-measured): `20260831-052456-effc505.md`'s own `cold` row at this
    exact MOS/temp/VDD corner (`typical`/-40C/2.97V), N=64, is a genuine
    in-window **PASS**: `vctrl_final` = 1.561 V, `t_lock` = 5.82e-05 s. That
    is this corner's own independently-measured, real lock point -- roughly
    **0.86 V below** where the `relock` extended run above is stalled
    (2.42 V), not "close and still closing." And where `relock`'s plateau
    does move (the +3.54 mV net drift above), it moves AWAY from that
    reference point, not toward it.
  - **Supplementary probe** (uncommitted -- a hand-modified copy of
    `tb_lock_time.sp` kept only under `/tmp`, never staged, that additionally
    saves/`wrdata`s `v(clk)` and `v(fb)` -- same "probe deck, not committed
    evidence" pattern `20260801-073931-eec269e.md` used for its own pilot-
    corner investigation): run at the identical corner/params/extended
    window, it reproduced `vctrl_final`/`dn_lvl` **bit-for-bit** (2.42022 V /
    1.71108 V), confirming the extra probe nodes do not perturb the circuit.
    Reading `fb`'s rising-edge period directly off the probe:
    | Window | mean fb period | fb frequency | fb / ref (20 MHz) |
    |---|---|---|---|
    | [100,300] ns (just after release) | 31.48 ns | 31.77 MHz | 1.588x |
    | [1.5,1.8] us | 33.51 ns | 29.84 MHz | 1.492x |
    | [3.0,3.3] us | 33.42 ns | 29.92 MHz | 1.496x |
    | [3.7,4.0] us (window end) | 33.41 ns | 29.93 MHz | 1.496x |

    From t=1.5us onward, `fb`'s rate is flat to within 0.3% through the end
    of the extended window -- **the frequency error is not shrinking any
    further either**, over the same span `vctrl` itself stops moving.
    `design/pfd.sch`'s own SR-latch description (the same one
    `20260801-073931-eec269e.md` cites): an FB edge SETs the `dn` latch, a
    REF edge SETs `up`, and both share one reset -- so a persistently-faster
    FB should keep `dn` set, waiting on REF's rarer edges for the shared
    reset. **Unlike `20260801-073931-eec269e.md`'s pilot corner (which found
    the OPPOSITE: `up` dominant despite FB running faster than REF)**, this
    corner's measured `up`/`dn` duty matches that naive expectation: `dn`
    reads HIGH for 53-76% of 200ns-binned samples across the window (`up`
    stays pinned near 3.5% throughout, essentially unchanging). `dn`'s own
    duty fraction is NOT flat, though -- it declines slowly from 0.755
    (t~1.3us) to 0.574 (t~3.9us) even while `fb`'s period and `vctrl` are
    both essentially flat over the same span. **This record does not
    resolve that discrepancy**; it is measured and reported, not explained
    -- see Limitations.
  - **Reading against #284's Acceptance Criteria**: at this corner, the
    evidence supports **option (b)** -- `vctrl` and the underlying `fb`/`ref`
    frequency error have **stalled**, not merely slowly converging, well
    before the (already only 2x-extendable) window ends, and well short of
    this same corner's own independently-measured locked operating point.
    This reads as a genuine loop-convergence question, not a window-too-
    short artifact -- **flagged to `loop-dynamics` (#10)**, per this
    repository's existing root-cause routing convention (see
    `sim/CHARACTERIZATION.md`'s `supply-sensitivity` row for the same
    pattern of routing a design-margin finding to the owning campaign rather
    than absorbing it here). This record does **not** re-derive why the
    loop stalls at this particular voltage (that needs `loop-dynamics`'s own
    small-signal/large-signal analysis, or a dedicated large-frequency-error
    PFD acquisition testbench per `20260801-073931-eec269e.md`'s own open
    item) -- it establishes THAT it stalls, with a quantified, reproducible
    waveform.
  - **Limitations, stated plainly**: this is **one** of the 131 non-rail-

    same declining-duty-fraction wrinkle recur generally is an open question
    this record does not answer. The declining `dn`-duty-fraction trend
