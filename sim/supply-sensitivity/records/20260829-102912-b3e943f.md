# Record 20260829-102912-b3e943f

- **Record ID**: 20260829-102912-b3e943f
- **Claim**: #242 -- #241/#243 added `sim/lib/simenv.sh::simenv_apply_omp_pin`
  (opt-in `OMP_NUM_THREADS=1` pin against ngspice's own internal OpenMP
  threading) and wired it into `sim/supply-sensitivity/testbench/run.sh`, the
  campaign that originally surfaced the ~55x self-oversubscription regression
  in #58. #241/#243's own verification window was confounded by a concurrent
  worktree running its own `sim/supply-sensitivity` campaign on the same
  8-core host, so no clean wall-clock before/after was captured. #242 asks:
  on a genuinely idle host, what is that before/after?

  **The answer this record found is not the number #242 asked for.** Direct
  process inspection shows `OMP_NUM_THREADS=1` makes **no measurable
  difference to ngspice-46's own thread count** for
  `sim/supply-sensitivity`'s closed-loop lock deck -- it spawns 8 OS threads
  identically with and without the pin. That finding is confound-immune (a
  `/proc/<pid>/status` reading, not a wall-clock number) and it answers the
  deeper question #242 was really asking -- "does the pin help this
  campaign" -- more directly than a wall-clock pair can, because no
  wall-clock pair on this shared host can be trusted to isolate the pin's
  effect from host contention (demonstrated live during this record's own
  build -- see "Confound observed live" below). A wall-clock pair was
  attempted anyway and is reported for completeness, explicitly flagged as
  not usable as a clean speedup/slowdown claim.

  This is the "pin is not effective for this deck" outcome #242's own
  Curator enhancement named as a valid, reportable result in its own right
  ("do not force a fix onto a mechanism the evidence doesn't support; open a
  new issue ... instead"). Follow-up filed: #244.

- **Methodology / criteria / limitations**:
  - **Why not "run `run.sh` twice" literally**, as #242's acceptance
    criteria ask: a first attempt (`./run.sh --check`, a single external
    ngspice invocation, no `xargs` fan-out) measured **8m10.248s real /
    48m50.051s user** for one steady-state corner with the pin already
    active (`OMP_NUM_THREADS=1`, confirmed exported by `simenv_apply_omp_pin`
    before the recursive `--one-lock` invocation). That single-point cost
    means a full reduced-grid pair (calibration + steady-state + power-split
    + step/ramp, x2 for with/without) would run to multiple hours on this
    8-core host, and -- per "Confound observed live" below -- remains exposed
    to the same class of confound #241/#243 already hit, this time from a
    **different repository's** agent fleet sharing the same physical host,
    which this issue has no mechanism to exclude for a multi-hour window.
    Given the mechanism-level finding below already answers the motivating
    question, that multi-hour run was not pursued further; #244 is filed for
    any future attempt.
  - **Isolated single-invocation test** (matching #146's own
    before/after-one-deck methodology, and avoiding `run.sh`'s own
    `xargs -P` fan-out so the pin's per-PROCESS effect can be read cleanly
    before considering process-level oversubscription at all): the deck
    above, run directly as `ngspice -b -o ngspice.log deck.sp` from a scratch
    copy, twice, differing only in `OMP_NUM_THREADS`:
    - **A ("with the pin")**: `OMP_NUM_THREADS=1 bash -c 'time ngspice -b -o
      ngspice.log deck.sp'`. Confirmed via `/proc/<pid>/environ` that the
      running ngspice process itself carried `OMP_NUM_THREADS=1`.
    - **B ("without the pin")**: `env -u OMP_NUM_THREADS bash -c 'time
      ngspice -b -o ngspice.log deck.sp'`. Confirmed via `/proc/<pid>/environ`
      that no `OMP_NUM_THREADS` was present.
  - **Thread count, read directly from `/proc/<pid>/status` (`Threads:`
    line) while each run was in progress, cross-checked against `ps -eLf`
    LWP counts**: **8 threads in both A and B**, no difference. This is the
    load-bearing, confound-immune result.
  - **Confound observed live, on the wall-clock numbers only**: run B's
    16m21.593s (below) overlaps a window in which `uptime`'s load average
    rose from ~0.1 (this record's own idle-host baseline) to 8.65 / 11.42 /
    9.87 (1/5/15-min, sampled at 10:26:09 UTC, moments after B completed).
    `ps aux` at that moment showed a **`sg13g2-bandgap`** repository's
    `/loom:sweep 141` agent (a different repository entirely, sharing this
    same physical host) having started at 10:10:xx UTC -- inside run B's
    10:10ish-10:26 window. This is the same class of shared-host confound
    #241/#243 disclosed for a same-repo sibling worktree, except this
    instance is **cross-repository** and outside anything this issue or
    repo's own worktree bookkeeping can observe or exclude in advance --
    `pgrep -fa ngspice` and this repo's own `.loom/worktrees/` listing, the
    two checks this record's own idle-host confirmation used, cannot see a
    sibling repository's agent fleet starting a CPU-heavy job on shared
    infrastructure. **The wall-clock numbers below must not be read as "the
    pin causes a 2x slowdown"** -- the thread-count evidence above already
    shows the pin made no difference to what ngspice itself did in either
    run; the wall-clock gap is attributable to the observed external
    contention, not to `OMP_NUM_THREADS`.
  - **A plausible root cause for the thread-count finding** (not confirmed,
    handed to #244): `strings $(which ngspice)` on this build lists both
    `num_threads` and `omp_set_num_threads` as linked symbols, consistent
    with ngspice maintaining its own internal thread-count setting (e.g. a
    `.spiceinit`/`set num_threads=N` control per ngspice's own manual) that
    calls `omp_set_num_threads()` itself -- which would silently override
    whatever `OMP_NUM_THREADS` the environment carries, exactly matching what
    was observed. `#146`'s `mc-cp-mismatch` deck (a Monte-Carlo
    charge-pump-only bench, much smaller than the full closed-loop PLL this
    deck simulates) measured and confirmed a genuine ~44x improvement from
    the identical environment-variable pin on the identical ngspice binary,
    so the mechanism the pin exploits (limiting BSIM model-evaluation
    threads) is real -- but this deck's dominant cost may instead sit with
    the KLU direct solver's own thread pool factoring the larger closed-loop
    Jacobian, which this hypothesis suggests is not governed by
    `OMP_NUM_THREADS` at all.
  - **Limitations**: single operating point; no `xargs`-level external
    process concurrency exercised (so this record makes no claim about
    process-level oversubscription specifically, only about the
    per-process thread-count effect the pin is supposed to produce before
    process-level concurrency is even considered); wall-clock numbers
    confounded as described and not usable as a clean claim in either
    direction; the ngspice-level root cause is a hypothesis from `strings`
    output, not verified against ngspice's source or documentation.

- **Result**:

  | Run | `OMP_NUM_THREADS` (confirmed via `/proc/<pid>/environ`) | Threads (`/proc/<pid>/status`) | Wall (real) | User | Sys |
  |---|---|---|---|---|---|
  | A ("with the pin") | `1` | 8 | 7m44.875s | 46m17.748s | 0m4.286s |
  | B ("without the pin") | *(unset)* | 8 | 16m21.593s | 80m45.311s | 0m5.361s |

  Both runs' user/real ratios are consistent with the SAME degree of
  multithreaded work (~6.0x for A, ~4.9x for B -- both point to roughly 5-6
  threads doing real concurrent work, not 1), which is the arithmetic
  restatement of the `Threads: 8` finding above: **the pin did not serialize
  this deck's execution in either run.** The ~2.1x wall-clock gap between A
  and B tracks the confound described above, not `OMP_NUM_THREADS`.
