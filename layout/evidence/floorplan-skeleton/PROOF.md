# PLL floorplan block-placement skeleton — DRC run (issue #17)

Generated by `python3 -c "from floorplan import skeleton; skeleton.build(...)"`
(see `layout/floorplan/skeleton.py`) followed by
`python3 layout/run_pv.py drc pll_floorplan_skeleton.gds --top
pll_floorplan_skeleton`. See `layout/floorplan/PLL-FLOORPLAN.md` for the
floorplan this skeleton implements and what running it through DRC does and
does not prove.

## What this is, and is not

This is **not** a signoff DRC-clean claim about the PLL's physical design.
`design/` has no top-level layout view for `vco`, `pfd_cp`, or
`divider_chain`/`lock_detector` yet, so there is no real device geometry for
those blocks to be DRC-clean *or* dirty. What this skeleton is: one boundary
rectangle per block (plus two real, as-drawn sub-geometries — the loop-filter
C1/C2 array from DR-006 and the VCO's committed 22 pF decap from `vco.sch`),
all drawn on GDS layer 0/datatype 0 (`DIEAREA`), positioned per
`PLL-FLOORPLAN.md`'s isolation and supply-routing plan.

Layer (0, 0) carries **no rule** in this PDK's DRC deck — confirmed by
grepping every rule file under
`$PDK_ROOT/libs.tech/klayout/drc/rule_decks/*.drc` for a reference to it
(none). So this DRC run is clean **by construction** (there is no rule that
could fire against this layer), not because the floorplan's real geometry
has been checked. The value of running it anyway is exercising #16's DRC
flow against a multi-shape, multi-block layout rather than only the single
trivial cell `layout/evidence/inv-tb-proof/` proves the flow on — a different
kind of coverage (does the flow handle a layout with several disjoint
boundary regions and text labels?), not a stronger DRC claim.

### Why it could drift, and what now stops it

Through #398 this module had `build(outdir)` and **no CLI**, so this file
documented regeneration as `python3 -c "from floorplan import skeleton;
skeleton.build(...)"` — an ad-hoc one-liner that `harness/reproduce.py` could
not invoke, which is precisely why this was the one committed block GDS the
reproducibility guard had to exclude by name. `skeleton.py` now has a
`main()` taking `--outdir`, matching every other generator in the repository,
and the entry has moved out of `reproduce.py`'s `EXCLUDED` and into its
`BLOCKS`:

```
$ python3 -m harness.reproduce          # from layout/
...
ok    evidence/floorplan-skeleton/pll_floorplan_skeleton.gds
26/26 committed block GDS files reproduce from their generators
```

So a seventh silent move of the plan is no longer possible: it fails
`layout/tests/test_gds_reproducibility.py` at the commit that introduces it —
including a move that, like `fe400132` above, edits a VCO sub-block and never
touches `skeleton.py`.
